# ADR-0001: Render video effects in Remotion instead of assembling them with FFmpeg

- **Status:** Accepted
- **Date:** 2026-09-27
- **Decision:** Use Remotion's composition model and `@remotion/renderer` for DemoForge export rendering. Keep FFmpeg available in the worker image as a runtime utility, but do not build the effect pipeline by concatenating FFmpeg filters and generated media segments.

## Context

DemoForge records a source WebM and persists an edit decision list (EDL). The
export pipeline needs to support cuts and visual effects while producing MP4
outputs at the supported aspect ratios.

The earlier export implementation used FFmpeg directly for scale/pad work.
That approach becomes increasingly awkward as the EDL grows: cuts require
timeline assembly, text needs escaping when expressed as an FFmpeg
`drawtext` expression, and freeze frames require splitting or duplicating
source media and then re-concatenating it.

Remotion already models the output as a frame-based composition. Its
`OffthreadVideo` can read the source URL during rendering, `Sequence` can place
cut clips back-to-back, and `Freeze` can hold a displayed frame without
changing the composition's own clock.

## Decision

Use a single Remotion `Demo` composition driven by:

```text
{ videoUrl, edl }
```

The renderer calls `selectComposition()` and `renderMedia()` with those
`inputProps`. Output dimensions are overridden from the requested aspect-ratio
table.

The EDL is expressed directly in the composition:

- each retained clip is a `Sequence`;
- each clip trims the source with `OffthreadVideo`;
- effects are matched against source time after mapping the output frame back
  through the retained clips;
- `freeze-frame` uses Remotion's `Freeze` around `OffthreadVideo`;
- text is rendered as React/JSX so React handles text escaping rather than
  constructing an FFmpeg filter string.

The Remotion composition is bundled once during the worker build. Export jobs
reuse that bundle instead of running a webpack bundle step for every export.

## Freeze-frame rule

A freeze-frame effect is authored in source-time seconds. Within the affected
clip it is converted into Sequence-relative frames. `Freeze` holds the
`OffthreadVideo` display at the selected frame while the composition timeline
continues to advance.

The wrapper remains mounted while the freeze toggles; only its `active` state
changes. This avoids remounting `OffthreadVideo` at the start/end of a freeze.

A freeze therefore holds the video image only. Other effects continue to use
the natural source-time mapping rather than treating the composition clock as
paused.

## Consequences

### Positive

- Cuts and effects share one timeline model.
- Freeze frames do not require media splitting and re-concatenation.
- JSX text is not interpolated into an FFmpeg command/filter string.
- The renderer's output dimensions can be selected per export without changing
  the source video.
- Future Remotion-native effects can be added without redesigning an FFmpeg
  command pipeline.

### Negative

- Export requires headless Chromium and the Remotion runtime.
- The render process needs more CPU/memory than a simple request handler.
- A production deployment needs a worker environment capable of running
  Chromium reliably.
- FFmpeg is no longer the primary composition engine, so FFmpeg-specific
  filters are not the source of truth for effect semantics.

## Deployment implication

The renderer must not run in the normal Next.js request process. The export
function belongs in a dedicated Inngest worker with the Chromium runtime
installed. The web application only creates the export record and sends the
`demoforge/export.requested` event.

This keeps the web target small and lets the worker scale independently from
interactive web traffic.
